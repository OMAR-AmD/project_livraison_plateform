# Deploying to the public cloud (Render, free tier)

This is the runbook for the `public Cloud` half of the Industrialization
baseline. It is short on purpose: `render.yaml` describes the whole stack, so the
work is mostly clicking Apply and then verifying that what came up is what was
described.

Everything below has been written against Render's current published behaviour.
Where a claim could not be tested from this machine (anything requiring an
account) it says so explicitly rather than being stated as fact.

---

## 0. Why Render and not the alternatives

Checked, not assumed:

| Provider | Reality as of this writing |
| --- | --- |
| **Render** | Free web services (512 MB, sleeps after ~15 min idle), free Postgres, free Redis-compatible Key Value. **No card required.** |
| Railway | Permanent free plan exists but grants **$1/month** of credit at 0.5 GB per service. The backend alone exceeds that. Hobby ($5/mo) is paid. |
| Fly.io | Their own docs: *"There is no 'free account/free tier' on Fly.io."* Trial only. |
| Oracle Always Free | Genuinely permanent, but capacity is frequently unavailable and signup is often rejected. Bad bet against a deadline. |

The three free-tier limits that matter, stated plainly because they belong in the
report rather than being discovered by the examiner:

1. **Cold starts.** Free web services sleep after ~15 minutes idle and take
   ~1 minute to wake. The first request of a demo pays that.
2. **Free Postgres is deleted 30 days after creation** (14-day grace, then gone).
   Fine for a coursework demo. Fatal as a production plan. No amount of code
   defends against it; only money does.
3. **Free Key Value is in-memory and 25 MB.** Costs nothing here — fraud trails
   carry a 6-hour TTL and are rebuilt by the next position update.

## 1. What only you can do

The deploy needs an account, and that is the one step nobody else can perform.

1. Create an account at <https://render.com> (GitHub sign-in is fastest; no card).
2. **New → Blueprint**.
3. Point it at this repository. Render reads `render.yaml` from the repo root and
   shows the resources it is about to create.
4. **Apply.**

Render creates, in one pass: `swiftdeliver-db` (Postgres), `swiftdeliver-cache`
(Key Value), `swiftdeliver-backend`, `swiftdeliver-frontend`.

Nothing needs to be typed by hand. `JWT_SECRET_KEY` is generated by Render, and
the database and cache credentials are wired by reference — the blueprint never
contains a secret, so there is nothing to leak out of this file or out of git.

## 2. Verify it, do not assume it

The build taking a while and going green is not the same as the platform
working. Four checks, in order. Substitute the real hostnames — if a name was
already taken, Render appends a suffix and the dashboard shows the real one.

```bash
# 1. The backend is alive AND the AI component is inside the running process.
#    This is the single most important line in this document: it proves the
#    container reachable from the internet loaded the fraud model.
curl -s https://swiftdeliver-backend-j47m.onrender.com/api/v1/health
# expected: {"status":"UP","fraudModel":"loaded","fraudTrees":60}

# 2. The frontend serves, and its proxy reaches the backend.
#    A 401/405 here is correct and means the rewrite works -- the request
#    reached the backend, which refused it for lack of a token. A 502 means
#    BACKEND_URL is wrong; see step 3.
curl -s -o /dev/null -w '%{http_code}\n' https://swiftdeliver-frontend.onrender.com/login
curl -s -o /dev/null -w '%{http_code}\n' https://swiftdeliver-frontend.onrender.com/api/v1/health
# expected: 200 then 200 (the proxy passes the public health path through)

# 3. The demo accounts exist in the cloud database.
#    A token here means Postgres accepted the connection, Hibernate created the
#    schema, and the demo seeder ran -- not merely that a web server is up.
curl -s -X POST https://swiftdeliver-backend-j47m.onrender.com/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@swift.com","password":"password123"}'
# expected: a JSON object containing a non-empty "token"

# 4. A body the server cannot read is the caller's error, not a server fault.
#    This answered 500 before the error mapping was fixed, so a 500 here means
#    the deployed image predates the source -- which is exactly what a stale
#    build looks like from the outside.
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  https://swiftdeliver-backend-j47m.onrender.com/api/v1/auth/login \
  -H 'Content-Type: application/json' -d '{"email": '
# expected: 400

# 5. Signing out revokes the token, and a failed-login burst is cut off.
#    Both controls are server-side, so neither is visible by clicking around.
#    Note: signing out ends every admin session, including this one.
TOKEN=$(curl -s -X POST https://swiftdeliver-backend-j47m.onrender.com/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@swift.com","password":"password123"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["token"])')
curl -s -o /dev/null -w 'logout:  %{http_code}\n' -X POST \
  https://swiftdeliver-backend-j47m.onrender.com/api/v1/auth/logout \
  -H "Authorization: Bearer $TOKEN"                       # expected: 200
curl -s -o /dev/null -w 'revoked: %{http_code}\n' \
  https://swiftdeliver-backend-j47m.onrender.com/api/v1/users/me \
  -H "Authorization: Bearer $TOKEN"                       # expected: 401 or 403
for i in 1 2 3 4 5; do
  curl -s -o /dev/null -X POST https://swiftdeliver-backend-j47m.onrender.com/api/v1/auth/login \
    -H 'Content-Type: application/json' \
    -d '{"email":"nobody@example.com","password":"wrong"}' || true
done
curl -s -o /dev/null -w 'limited: %{http_code}\n' -X POST \
  https://swiftdeliver-backend-j47m.onrender.com/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"nobody@example.com","password":"wrong"}'   # expected: 429
```

Then open the frontend URL, sign in as `admin@swift.com` / `password123`, and
confirm the dashboard renders.

**Warm both services about 60 seconds before demoing.** The cold-start penalty is
real and it is the one thing that will make a working platform look broken in
front of an examiner. Loading both URLs once is enough.

## 3. The one field that may need fixing

`BACKEND_URL` in `render.yaml` is set to
`https://swiftdeliver-backend-j47m.onrender.com`.

It has to be a literal because Next.js inlines its rewrites at **build** time
(`next.config.mjs`), while the backend's public URL does not exist until the
backend has been created. `swiftdeliver-backend` was already taken, so Render
assigned the suffix `-j47m`, and that real host is what the frontend's build
arg must carry. A future blueprint apply will very likely get a different
suffix, so expect to update this line then.

**Symptom if it is wrong:** the site loads, the login page renders, and every API
call fails with 502. The frontend itself looks fine, which is what makes it worth
a section of its own.

**Fix:** Dashboard → `swiftdeliver-frontend` → Environment → set `BACKEND_URL` to
the backend's real URL (copy it from the backend's page) → **Save & Deploy**.
Render translates the variable into a Docker build argument on the rebuild, so
the rewritten proxy picks it up. Nothing else needs redeploying.

## 4. What is different from the local stack

**OSRM.** Locally it is a container built from a map extract that is roughly
1.5 GB — no free tier will hold it. Rather than deploy a platform whose
auto-dispatch silently assigns nobody (orders sit `PENDING` until an admin
intervenes by hand), `OSRM_BASE_URL` points at OSRM's official public demo server,
`https://router.project-osrm.org`. That was verified answering `Ok` with a real
routing request before it was written down. It is someone else's machine and it
is rate-limited: acceptable for a demo, not acceptable for production, and worth
saying out loud rather than letting it look like a self-hosted capability.

**The chatbot.** Chat requires Ollama and `pgvector`, neither of which exists on
this free tier. The assistant degrades — it reports itself unavailable rather
than erroring — and the rest of the platform, including the fraud detection,
is unaffected. The innovation is the fraud model, which is pure Java evaluated
in-process and has no such dependency.

**The database has a 30-day life.** Render deletes a free Postgres after 30 days
with no backup: the accounts created through `/register`, the orders, the seals
and the `tokenVersion` values all go. The demo seeder restores `admin@swift.com`,
the `courier1/2` and `client1..3` accounts and the demo orders on the next start,
but it does not re-create a sealed delivery, so a proof demonstration needs a
courier run first. More bluntly, once the database is gone the backend never
reaches Tomcat (`ddl-auto: update` runs during startup), so the whole site answers
502 until the database is recreated. Recreate it — or re-Apply the blueprint —
within 30 days of any demonstration. That is a limit of the free tier, not a
defect in the code, and the honest thing is to say so rather than discover it in
front of an examiner.

**Regions.** `frankfurt` is set per-resource, not once at the root, and cannot be
changed after creation. It is the lowest-latency region for a European audience
and the OSRM demo server used here is also in Europe.

## 5. Deploys after the first one

Each service has `autoDeployTrigger: checksPass`, so a push to the default branch
deploys **only if the GitHub Actions checks are green**. That is the CI/CD chain
in its entirety: GitHub Actions is the gate, Render is the target.

If pushes ever stop producing deploys, Render is not seeing the check runs.
Switch the trigger to `commit` in the service's settings — the chain still works,
just without the gate.

## 6. Verifying the blueprint without deploying it

Two checks, deliberately different:

```bash
# Structural and hermetic. Runs in CI. Catches what a schema cannot: an
# environment variable referencing a database or service this file never
# declares -- which validates cleanly and then hands the backend an empty host.
python scripts/check_render_blueprint.py render.yaml

# Full validation against Render's published JSON Schema. Needs the network,
# so it is run by hand before a release rather than in CI.
python scripts/validate_render_blueprint.py render.yaml
```

The second one is worth running because it has already caught three real defects
in a file that read as correct: `off` being parsed as the boolean `false` under
YAML 1.1, a `region` field placed at the root where it does not exist, and
`property: databaseName` where Render's schema enumerates `database`.
